Job Recommender — Design Decisions & Tradeoffs

A walkthrough of the key architectural choices made while building a two-stage ML-powered job retrieval pipeline, from model selection through deployment.

Python FastAPI Streamlit sentence-transformers Docker Hugging Face

Retrieval Architecture

Core Decision

Two-stage pipeline over single-stage retrieval

The pipeline uses a bi-encoder for fast candidate retrieval followed by a cross-encoder for precise reranking, rather than relying on a single model to do both.

A bi-encoder encodes the query and each document independently into fixed vectors, making it fast enough to scan thousands of jobs at query time. The tradeoff is that it cannot model interactions between query tokens and document tokens — "Python RAG engineer" and "Python pipeline manager" may score similarly despite being very different roles.

The cross-encoder processes the query and document together through a transformer, allowing full cross-attention between every token pair. This produces much more accurate relevance scores, but cannot be pre-computed, making it too slow to run against the full corpus.

Why not single-stage? Bi-encoder alone loses fine-grained token interactions. Cross-encoder alone is too slow to run against 15,000 jobs per query.
Why two-stage? Bi-encoder narrows to 50 candidates cheaply; cross-encoder reranks those 50 accurately. Best of both.
Model Selection

all-MiniLM-L6-v2 for retrieval, ms-marco-MiniLM-L-6-v2 for reranking

all-MiniLM-L6-v2 was chosen for the bi-encoder stage. It is small (22M params), fast, and produces 384-dimensional embeddings that can be pre-computed and stored. Embeddings are normalized so dot product equals cosine similarity, avoiding a division at query time.

cross-encoder/ms-marco-MiniLM-L-6-v2 was chosen for reranking. It was fine-tuned on MS MARCO, a large dataset of query/passage relevance judgments derived from real search queries. It understands relevance in natural language, not just keyword overlap.

Candidate Pool Sizing

max(top_k × 10, 50) as the retrieval pool

The number of candidates passed to the cross-encoder matters. Too few and the reranker has nothing meaningful to reorder. Too many and it becomes slow.

A floor of 50 ensures the reranker always has a meaningful pool. The top_k × 10 multiplier scales the pool proportionally when callers request more results — preventing a silent cap where fewer candidates than requested are returned.

API Design

Startup Loading

Models and embeddings loaded once at startup via FastAPI lifespan

Loading SentenceTransformer, CrossEncoder, and the 22MB embeddings matrix on every API request would add 2–5 seconds of latency per call. FastAPI's lifespan hook runs once when the server starts, stores these objects on app.state, and makes them available to every request handler without reloading.

Tradeoff Slightly slower cold start in exchange for fast, consistent per-request latency.
Alternative considered Per-request loading — rejected because it made the API unusable, taking 3–6 seconds per search.
Validation

Input validation at both the frontend and backend

An empty query is blocked in two places: Streamlit checks before making the API call (fast, user-friendly), and Pydantic's Field(min_length=1) on the SearchRequest model rejects it at the API boundary (defensive, since the API can be called directly).

This avoids depending on the frontend as the sole guard — any client calling the API directly gets a proper 422 response rather than a confusing downstream error.

Data & Scale

Dataset Size

15,000 jobs over the full 1.62M-row source dataset

The source Kaggle dataset contains 1.62 million job postings. Embedding the full corpus would produce a ~1.2GB embeddings file and require significant RAM at startup — impractical for a free-tier deployment.

15,000 jobs keeps the embeddings file under 25MB, loads instantly, and is more than sufficient to demonstrate retrieval quality. For a portfolio project, demonstrating the pipeline is the goal, not exhaustive coverage.

Data Hosting

Job data hosted on Hugging Face Datasets, not bundled in the repo

Git repositories have size limits, and Hugging Face Spaces rejects files over 10MB. Rather than bundle the job JSON and embeddings directly, they are hosted as a public Hugging Face Dataset (devin-z/job-pipeline-data) and downloaded at startup using hf_hub_download().

This keeps the code repository lightweight, separates data versioning from code versioning, and fits the free-tier constraints of both GitHub and Hugging Face Spaces.

Deployment

Architecture

Split deployment: FastAPI on Hugging Face Spaces, Streamlit on Streamlit Community Cloud

Docker Compose runs both services together locally. In production, they are deployed separately — the FastAPI backend to Hugging Face Spaces (Docker SDK) and the Streamlit frontend to Streamlit Community Cloud.

Hugging Face Spaces does not support multi-container Docker Compose in production, so a combined deployment would require a process manager. Splitting is simpler, keeps concerns separate, and both platforms offer free tiers suited to their respective service type.

Alternatives considered Railway (Docker Compose support, but requires paid plan). Render (free tier with 15-minute cold-start spin-down). Both rejected on cost or UX grounds.
Why Hugging Face for the API? Free Docker deployment, good ML ecosystem visibility, and no cold-start penalty on the API tier.
Container Networking

Service names over localhost for inter-container communication

Each Docker container has its own isolated network namespace — localhost inside the Streamlit container refers to that container itself, not the FastAPI container. Docker Compose creates a shared bridge network and assigns each service a DNS name matching its service name in docker-compose.yml.

The Streamlit app uses an API_URL environment variable (defaulting to http://127.0.0.1:8000 for local development) so the same code works in both environments without modification.
